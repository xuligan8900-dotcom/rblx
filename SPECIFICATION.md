Ты — автономный senior Roblox game developer, Luau architect, gameplay programmer, technical game designer, UI/UX designer, procedural environment developer, economy designer, security engineer и QA engineer.

Твоя задача — создать с нуля качественную, расширяемую, многопользовательскую Roblox-игру **MUTATION GARDEN: GENETIC PARADISE**.

Это production-oriented проект, а не демонстрация и не набор отдельных скриптов.

**Основная цель:** создать работающую игру, которую можно открыть в Roblox Studio, протестировать, улучшать и подготовить к публикации.

Не ограничивайся составлением плана. После планирования приступай к непосредственному созданию проекта и продолжай реализацию последовательно.

Все игровые механики должны быть действительно реализованы. Избегай псевдокода, ненужных TODO, пустых заглушек, неработающих кнопок и фиктивных систем.

Если у тебя нет прямого доступа к Roblox Studio, создай максимально полный файловый проект, скрипты генерации мира, конфигурации, автоматизированные тесты и точные инструкции для проверки в Studio.

Не выдумывай результаты тестов, несуществующие Roblox API, Asset ID и подключения к внешним сервисам.

Не прерывайся после каждого этапа ради подтверждения. Работай последовательно в рамках доступного времени и инструментов, сохраняя понятный прогресс в репозитории.

## Hybridization

Игрок выбирает два растения.

Сервер проверяет:
- Владение
- Совместимость видов
- Наличие необходимых ресурсов
- Статус растений
- Доступность лаборатории
- Ограничения по времени

Затем создаёт потомка.

Примерный алгоритм:
1. Проверить родителей.
2. Определить совместимость.
3. Выбрать наследуемые аллели.
4. Применить вероятность мутаций.
5. Проверить специальные рецепты гибридизации.
6. Создать уникальный идентификатор потомка.
7. Рассчитать фенотип.
8. Сохранить результат.
9. Показать анимацию эксперимента.

Принципиально важно:

**Исход эксперимента рассчитывается исключительно на сервере.**

Не использовать клиентские значения случайности.

## Trading

Обмен должен быть серверно-авторитетным.

Обязательная схема:
1. Игрок A отправляет запрос.
2. Игрок B принимает.
3. Открывается интерфейс обмена.
4. Каждый игрок предлагает предметы.
5. Предметы валидируются и резервируются сервером.
6. Любое изменение предложения сбрасывает подтверждения.
7. Оба игрока подтверждают конечный список.
8. Выполняется финальная проверка.
9. Сделка проводится как атомарная операция внутри серверного состояния.
10. Результат фиксируется для сохранения.

Обработать:
- Выход игрока
- Отмену
- Таймаут
- Недостаток предметов
- Повторную отправку запроса
- Изменение предметов
- Попытку дублирования

Не запускать обмен, если сохранение критических данных недоступно или состояние профилей небезопасно.

Для первой реализации разрешены обмены только между игроками одного сервера.

При использовании предметов с платным происхождением соблюдать ограничения PolicyService.

# 25. NETWORK SECURITY

Сервер является единственным источником истины.

Клиент отправляет намерение, но не итоговый результат.

Пример:

Неправильно:
Client → "Give me 100000 coins".

Правильно:
Client → "Sell plant with instanceId X".

Сервер:
- Проверяет владельца
- Проверяет растение
- Проверяет доступность продажи
- Рассчитывает награду
- Удаляет или резервирует предмет
- Начисляет валюту
- Отправляет результат

Обязательно:
- Runtime type validation
- Проверка диапазонов чисел
- Проверка math.isfinite
- Проверка строк и идентификаторов
- Rate limiting
- Cooldowns
- Проверка расстояния
- Проверка ownership
- Проверка доступности действий
- Защита от replay requests
- Защита от double spending
- Ограничение размера payload
- Ограничение частоты RemoteEvents
- Логирование подозрительных операций

Не доверять даже событиям ProximityPrompt без дополнительной серверной проверки.

Не передавать на клиент секреты, внутренние административные токены или приватную логику начислений.
